# v0.3.3 state synchronization and render delivery

## Confirmed truth and optimistic presentation

Each Dashboard now has one atomic v4 record containing confirmed entity states,
Home Assistant timestamps, optimistic overlays, operation metadata, the absolute
operation deadline and committed/requested/rendered revisions. An optimistic value
never replaces the confirmed value. A conflicting HA event or REST snapshot updates
confirmed truth while the overlay may remain visible only until the fixed deadline.

HTTP 2xx means only that Home Assistant accepted the service call. Binary operations
become `CONFIRMED` only after an HA event or REST snapshot contains `desiredState`.
Every terminal path uses `DashboardTerminalStateMachine.finish`, which clears the
overlay, records terminal metadata, advances the revision and requests a render.

## Deadline and startup recovery

Operations receive an immutable 12 second deadline at creation. A separate deadline
worker has no network constraint, so WorkManager retries cannot extend the operation.
At process start the app performs targeted REST reconciliation, sweeps persisted active
operations, finishes expired operations and resumes non-expired work. It also resumes
any render for which committed/requested revision is ahead of rendered revision.

## Render coordinator

All Dashboard updates are routed through a per-widget coordinator. It serializes one
widget, coalesces requests to the maximum revision and records `renderedRevision` only
after `GlanceAppWidget.update` succeeds. Failures are logged and schedule a short,
durable retry without blocking other widgets. Navigation remains local and uses the
same coordinator.

## Honor Launcher manual matrix

1. Command not applied: start from confirmed ON, tap OFF while HA remains ON, and verify
   automatic return to ON with no pending state within 12 seconds.
2. External state: change an entity in HA UI, another widget or a physical control while
   the process is alive; verify Dashboard changes without Refresh or tab switching.
3. Render recovery: verify Logcat sequence `REVISION_COMMIT` → `RENDER_FAILURE` →
   `RENDER_RETRY` → `RENDER_SUCCESS` and rendered revision catches committed revision.
4. Process death: create a pending binary action, kill the app process, wake the widget,
   and verify `STARTUP_SWEEP`, terminal operation and current HA truth.
5. Navigation: perform 20 rapid tab taps, including during action and refresh; the final
   tab must match the last tap and navigation must not wait for network work.

Only a physical Honor Launcher can validate RemoteViews apply latency, vendor process
management, scroll retention and real background WebSocket lifetime.
